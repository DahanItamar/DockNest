# Backup format v1

The payload file is DBM1 (4 ASCII bytes), a 12-byte random nonce, AES-256-GCM ciphertext, and the 16-byte authentication tag. The 16-byte header is authenticated as AAD. The encryption key is the 32-byte master key. SHA256 covers the entire encrypted file. Preserve the master key separately from the metadata database and payloads.

Plaintext is a gzip tar containing manifest.json, images.tar, and mount-I-J.tar files. The private manifest includes full Docker inspect configuration and snapshot image IDs; it contains secrets and must remain encrypted. Public database metadata excludes environment values and host source paths. Each mount archive preserves numerical UID/GID, modes, links, GNU tar ACLs and extended attributes. Committed snapshot images capture writable layers; mount archives capture attached data separately.

The source stops only containers previously running, verifies clean zero exit codes, copies mounts without hard links, commits writable layers, restarts and checks health, disables maintenance, then saves images and compresses. A detached local watchdog terminates the helper process group at its deadline before recovery, starts previously running containers, and clears maintenance only after health succeeds. Review recovery.json after a disconnect. Staging and snapshot images are retained after failures; disk use requires operator review. Watchdog does not survive source-host reboot: arrange a boot recovery service before production use.

Single-container new-copy restore is implemented with an explicit network-none configuration, fresh mount directories and no restart policy. It loads the captured image, starts the container and checks Docker health. Console access is returned; routing is a separate administrator action. Multi-container networking, custom port/path maps, archive links/devices, host privileges and replacement require reviewed adapters and are blocked. Linux Docker integration acceptance remains unvalidated on this development PC. Replacement has additional safety-backup and rollback requirements. Offline recovery must first authenticate the whole ciphertext to a private temporary file. Never pipe unauthenticated decrypted bytes into an extractor. Check paths, reject absolute/traversal names and links escaping destination, inspect configuration, load images, recreate isolated networks and new mount destinations, and create containers without privileged access or host namespaces. Original inspect settings contain credentials and must be handled as secrets. Do not reuse production ports, restart policies, or external connections. A checksum verifies transport integrity; it does not prove a working restored application.

Current capture blockers: Compose sites without explicit composeFiles/configFiles and externalReferencesConfirmed; privileged/device-backed containers; tmpfs and system mounts; shared mounts with outside running containers; no explicit exclusiveSourcesConfirmed assertion; non-root SSH; graceful exit code other than zero. External writers cannot be inferred from Docker alone: the administrator must confirm exclusive ownership. Database-specific shutdown proof beyond the configured clean-exit profile requires integration validation.

Maintenance HTML distribution over SSH is implemented; proxy maintenance uses an administrator-reviewed Nginx integration template. Distribution does not report readiness automatically. A readiness marker alone does not prove routing: public 503 and internal health probes are required. Configure TLS and JSON API responses independently. The default public probe accepts HTTP 503; verify its body marker manually to rule out unrelated 503s.

Retention removes only ordinary verified backups beyond the configured count after a new successful capture, and respects active download and restore records. Pinned backups are additional to the count. Interrupted jobs enter recovery_required and prevent further work on their server. Resolve source health and watchdog state before changing job status. Single-worker lock files survive unclean death and must be inspected before removal. Central restart does not silently assume remote recovery succeeded.
