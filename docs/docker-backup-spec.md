# אפיון מערכת גיבויים מרכזית לאתרי Docker

גרסה: 1.1  
תאריך: 01.10.2026  
סוג מסמך: דרישות מוצר, תהליכי עבודה ועקרונות מימוש

## 1. מטרת המערכת

לבנות מערכת Web עצמאית לניהול גיבויים של אתרי Docker על מספר שרתים. המערכת מותקנת באמצעות Docker על שרת גיבויים ייעודי עם מעבד מתאים ואחסון בנפח מספק.

מנהל המערכת מוסיף שרתים דרך SSH, בוחר אתרי Docker לגיבוי, מגדיר מתי לגבות וכמה גרסאות לשמור. כל הגיבויים נשמרים בשרת המרכזי, מסודרים לפי שרת, אתר ותאריך ושעת הגיבוי.

בעת הצורך אפשר לבחור נקודת גיבוי ולהוריד חבילת שחזור מלאה, או להפעיל שחזור אוטומטי לשרת המקורי או לשרת יעד אחר.

## 2. ההחלטות שסוכמו

- כל Docker אצל המשתמש מייצג אתר מלא, כולל אפליקציה, מסד נתונים, assets, קבצים והגדרות.
- המערכת חייבת לזהות את כל רכיבי האתר בפועל, לרבות נתונים שמחוברים לקונטיינר באמצעות volumes או bind mounts.
- מקובל להשבית את האתר במהלך יצירת העותק המקומי.
- התהליך הנבחר הוא: עצירה מסודרת → יצירת עותק מקומי של האתר → הפעלה מחדש → דחיסה והעברה לשרת הגיבויים.
- האתר אינו נשאר כבוי בזמן דחיסה או העברה ברשת.
- משך ההשבתה נמדד בפועל; אין התחייבות שכל אתר יגבה בתוך חמש דקות.
- אפשר להגדיר X גיבויים אחרונים לכל אתר, למשל שבעה גיבויים, אחד בכל יום.
- שתי הפעולות נדרשות: Download ו־Restore. בממשק משתמשים במונח Restore / שחזור במקום Load.
- תמיכה במקורות חיצוניים, כגון buckets ותיקיות נוספות, תהיה אפשרות הרחבה ולא תנאי לשימוש הבסיסי.
- דף תחזוקה מקומי בכל שרת אתרים הוא חלק מהגרסה הראשונה; הוא מנוהל ומופץ מה־Dashboard המרכזי ומוגש באמצעות Proxy נפרד מהקונטיינר המגובה. סעיף 19 מגדיר את התהליך המשולב.

## 3. הגדרת יחידת גיבוי

יחידת גיבוי נקראת „אתר”. ברירת המחדל היא קונטיינר יחיד שמכיל את האתר כולו. ניתן לאגד מספר קונטיינרים לאותו אתר אם בעתיד יופרדו האפליקציה ומסד הנתונים.

בחירת קונטיינר אינה מספיקה כשלעצמה: המערכת מציגה למנהל את רשימת הרכיבים שייכללו בגיבוי ומתריעה על רכיב חסר או לא נתמך. אין לסמן גיבוי כ„מלא” אם רכיב נדרש הושמט.

## 4. ארכיטקטורה

### שרת הגיבויים המרכזי

- Web Dashboard לניהול המערכת.
- API להגדרות, משימות, היסטוריה, הורדות ושחזורים.
- Worker לביצוע משימות ממושכות בנפרד מבקשות הדפדפן.
- Scheduler להפעלת גיבויים לפי תזמון.
- מסד נתונים למטא־דאטה ולמצבי משימות.
- אחסון קבוע לגיבויים, קבצים זמניים ולוגים.

כל המערכת מסופקת כחבילת Docker Compose. אין הכרח שכל רכיבי הניהול יהיו בתוך קונטיינר יחיד; מבחינת המשתמש זוהי מערכת אחת להתקנה ולניהול.

### שרתי המקור והיעד

- חיבור SSH מוצפן עם מפתח.
- Docker מותקן וזמין למשתמש החיבור עם ההרשאות הדרושות.
- מקום פנוי ליצירת עותק מקומי זמני.
- פקודות עזר או סקריפט עבודה עם גרסה ידועה, המופעלים דרך SSH.
- לא נדרש לחשוף Docker API לציבור.
- שחזור לשרת חדש מחייב בדיקת התאמה של מערכת ההפעלה, Docker וארכיטקטורת המעבד.

## 5. מסכי הממשק

### Dashboard ראשי

מציג מספר שרתים ואתרים, משימות פעילות, גיבויים מוצלחים וכושלים, גיבוי אחרון לכל אתר, ניצול אחסון ומשימות מתוכננות. כשל בהפעלת אתר מחדש מוצג בהבלטה.

### שרתים

הוספה ועריכה של שם, כתובת, פורט SSH, משתמש, מפתח וגיבוי למפתח מוצפן לפי הצורך. כפתור בדיקת חיבור מציג זמינות Docker, הרשאות, ארכיטקטורה ושטח פנוי. שינוי SSH host key מחייב אימות מפורש ולא מתקבל בשקט.

### בחירת אתרים

סריקת קונטיינרים והצגת שם, image, מצב, labels, שיוך Compose, mounts ופורטים. המנהל בוחר קונטיינר או קבוצה ומעניק שם קבוע לאתר. מזהה האתר נשאר קבוע גם אם הקונטיינר נוצר מחדש.

### הגדרות גיבוי לאתר

- הפעלה או השהיה של גיבויים אוטומטיים.
- תזמון, אזור זמן ושעת ריצה.
- מספר נקודות גיבוי לשמירה.
- אפשרות „גבה עכשיו”.
- רכיבים ותיקיות שנכללים בגיבוי.
- תיקיית staging מקומית בשרת המקור.
- זמן מקסימלי לעצירה מסודרת ולפעולות שונות.
- אפשרות לצירוף מקורות חיצוניים.
- הגדרות התראות ומשך השבתה צפוי, המבוסס על מדידות קודמות.

### היסטוריית גיבויים

סינון לפי שרת, אתר, תאריך וסטטוס. לכל גיבוי מוצגים מזהה, תאריך ושעה, מועד לכידת המצב, תחילת וסיום המשימה, גודל, משך השבתה, רכיבים שנכללו, גרסאות images, תקינות ולוגים מסוננים מסודות.

### הורדה ושחזור

לכל גיבוי תקין מוצגים כפתורי Download ו־Restore. מסך השחזור כולל בחירת שרת יעד, שחזור לעותק חדש או החלפת אתר קיים, מיפוי פורטים ותיקיות, בדיקת התאמה ואישור לפני כתיבה ליעד.

## 6. מה כולל גיבוי מלא

| רכיב | דרישה |
|---|---|
| Docker images | לשמור image מדויק לפי מזהה ו־digest כאשר קיים, ולא להסתמך רק על tag כמו latest |
| Volumes | כל ה־volumes שנדרשים לאתר, כולל נתוני מסד הנתונים |
| Bind mounts | כל התיקיות והקבצים המחוברים שנדרשים להפעלה |
| Assets | תמונות, סרטונים, מסמכים, קבצים שהועלו ותוכן סטטי |
| שכבת כתיבה של הקונטיינר | ללכוד שינויים נדרשים אם הנתונים נשמרו בתוך הקונטיינר עצמו; אין להסתפק ב־image המקורי |
| הגדרות הרצה | command, entrypoint, environment, restart policy, health checks והגדרות רלוונטיות אחרות |
| Compose | קובצי Compose, קובצי env והפניות לקבצים נדרשים, אם קיימים ונגישים |
| רשתות ופורטים | לשמור הגדרות ולבצע התאמה לשרת היעד |
| הרשאות קבצים | לשמר בעלות, UID/GID, הרשאות, קישורים ומאפיינים נדרשים |
| Secrets | גיבוי מוצפן של סודות שניתנים לקריאה; הפניות חיצוניות דורשות טיפול מפורש |
| Manifest | מפת רכיבים, גרסת פורמט, checksum, פרטי מקור ותלויות |
| הוראות שחזור | הסבר עצמאי להפעלה מחדש גם ללא מערכת הניהול |

אין להניח ש־docker save, docker export או docker commit לבדם מגבים אתר שלם: יש לטפל בנפרד בנתונים המחוברים ובהגדרות ההפעלה. אין להעתיק את תיקיית Docker הפנימית בשרת כתחליף לחבילת שחזור ניידת.

tmpfs, mounts מערכתיים, Docker socket ושירותים חיצוניים אינם נתוני אתר ניידים אוטומטית. המערכת מסווגת אותם ומציגה את התלויות במקום להעתיקם באופן עיוור.

## 7. תהליך גיבוי — העותק המקומי

### שלב א׳: בדיקות מקדימות כשהאתר עדיין פעיל

1. נעילת האתר למניעת גיבוי או שחזור מתחרים.
2. בדיקת SSH, הרשאות, קונטיינרים וכל מקורות הנתונים.
3. בדיקת מקום בשרת המקור ובשרת המרכזי; אומדן גודל אינו הבטחה לגודל הסופי.
4. יצירת מזהה משימה ותיקיית staging ייחודית מחוץ לתיקיות האתר.
5. שמירת מצב הקונטיינרים והגדרותיהם לפני העצירה.
6. אימות שמקורות משותפים אינם נכתבים בידי קונטיינר או תהליך אחר מחוץ ליחידת הגיבוי. במקרה כזה יש לתאם עצירה או לחסום את הגיבוי המלא עם הסבר.
7. שמירת images שאינם משתנים יכולה להתבצע מראש, כדי לצמצם את חלון ההשבתה.

### שלב ב׳: עצירה מסודרת

1. רישום זמן תחילת ההשבתה.
2. הפסקת כתיבות ועצירת האתר, workers ומסד הנתונים הרלוונטיים בסדר מוגדר.
3. אימות סיום תקין של התהליכים; בקונטיינר שמריץ כמה תהליכים יש לוודא שכל השירותים נסגרים כראוי.
4. עצירה בכוח או timeout אינם נחשבים אוטומטית לסגירה תקינה. במקרה כזה אין להבטיח גיבוי עקבי ויש לדווח ולנסות להחזיר את האתר לפעולה.

### שלב ג׳: יצירת עותק מקומי

1. העתקת כל הנתונים לתיקיית staging נפרדת כשהכתיבות נעצרו.
2. לכידת השינויים הנדרשים בשכבת הקונטיינר ובהגדרותיו.
3. יצירת manifest ראשוני ורישום מועד נקודת הגיבוי.
4. אימות שההעתקה הסתיימה בהצלחה ושהעותק אינו תלוי בנתונים הפעילים.
5. אין להשתמש בקישורים קשיחים לנתונים שהאתר ימשיך לשנות לאחר ההפעלה; העותק חייב להישאר יציב.

בגרסה הראשונה ניתן להשתמש בהעתקה מלאה מקומית. snapshots יתווספו רק עבור מערכות קבצים נתמכות ולא יהיו הנחה בסיסית.

### שלב ד׳: הפעלה מחדש

1. הפעלת הקונטיינרים שהיו פעילים קודם לכן, בסדר התלויות הנדרש.
2. קונטיינר שהיה עצור לפני הגיבוי אינו מופעל ללא בקשה מפורשת.
3. בדיקת מצב והפעלת health checks או בדיקת HTTP כאשר הוגדרו.
4. רישום משך ההשבתה והפעלת התראה אם האתר אינו חוזר לפעילות.

### שלב ה׳: עיבוד והעברה כשהאתר כבר פעיל

1. דחיסת העותק המקומי והצפנתו.
2. חישוב checksums והשלמת manifest.
3. העברה לשרת המרכזי לתיקייה זמנית של משימה לא גמורה.
4. בדיקת תקינות ושלמות בשרת המרכזי.
5. פרסום אטומי של נקודת הגיבוי כתקינה רק לאחר השלמת הבדיקה.
6. מחיקת staging מקומי לאחר אישור קליטה תקינה.
7. הפעלת מדיניות שימור הגיבויים.

כשל בהעברה אינו מצריך עצירה נוספת של האתר. אפשר לנסות להעביר שוב את אותו עותק מקומי, כל עוד הוא שמור ותקין.

## 8. עקביות מסד הנתונים והקבצים

במסלול הבסיסי שנבחר, כל השירותים שכותבים נתוני אתר נעצרים באופן מסודר לפני ההעתקה. כך קבצי מסד הנתונים וה־assets מועתקים ממצב שאינו משתנה במהלך ההעתקה.

המערכת חייבת לוודא שמסד הנתונים אכן נסגר כראוי; עצירת Docker אינה הוכחה לכך בפני עצמה. יש לתמוך בפרופילי עצירה לפי האתר ומסד הנתונים.

שחזור פיזי של מסד נתונים נעשה תחילה עם גרסת התוכנה התואמת לגיבוי. שדרוג גרסת מסד הנתונים הוא פעולה נפרדת.

אפשר להוסיף בהמשך מסלול גיבוי מקוון באמצעות כלי הגיבוי של מסד הנתונים, אך הוא אינו מחליף את מסלול העצירה שסוכם ואינו נדרש לגרסה הראשונה.

## 9. אחסון ושמירת גרסאות

מבנה לוגי לדוגמה:

```text
/backups/<server-id>/<site-id>/<timestamp>_<backup-id>/
    manifest.json
    payload.enc
    checksums.json
    restore-guide.md
```

שמות קריאים מוצגים בממשק; מזהים קבועים מונעים התנגשויות ושבירה בעקבות שינוי שם אתר. חבילת payload מכילה את ה־images, הנתונים וההגדרות בהתאם לפורמט.

- ברירת מחדל מוצעת: שבע נקודות גיבוי מוצלחות אחרונות לכל אתר.
- גיבוי יומי באותה שעה ייצור בדרך כלל שבע נקודות יומיות; אין יצירת נקודה מדומה ביום שבו גיבוי נכשל.
- כשל אינו גורם למחיקת גיבוי תקין קודם.
- מחיקה נעשית רק לאחר אישור גיבוי חדש תקין.
- ניתן להצמיד גיבוי כדי שלא יימחק; גיבוי מוצמד נשמר בנוסף למכסה הרגילה.
- גיבוי שמשמש להורדה או לשחזור מוגן ממחיקה עד סיום הפעולה.
- מחיקה ידנית דורשת אישור ומוגבלת לנתיבים שבבעלות המערכת.
- ניתן לשמור בגרסה הראשונה חבילות מלאות עצמאיות. אם בעתיד תתווסף שמירה אינקרמנטלית, המחיקה חייבת לשמר את כל התלויות של הגרסאות שנשארות.

גיבויי המערכת עצמם, מסד המטא־דאטה ומפתחות הפענוח דורשים תוכנית התאוששות. מומלץ לאפשר עותק נוסף מחוץ לשרת המרכזי, כדי שכשל שלו לא יאבד את כל הגיבויים.

## 10. Download — הורדה

המנהל בוחר אתר ונקודת גיבוי לפי תאריך ושעה ומוריד חבילה עצמאית מלאה. אין שינוי בשרת המקור או בשרת יעד.

החבילה כוללת נתונים, images, הגדרות, manifest והוראות שחזור. יש אפשרות להוריד חבילה מוצפנת ולפענח באמצעות כלי מתועד ומפתח שמוחזק בידי המנהל.

הורדות גדולות מוזרמות ללא טעינה מלאה לזיכרון. נדרשת תמיכה בהמשך הורדה שנקטעה ואימות שהקובץ שהורד שלם. הרשאת ההורדה נבדקת גם כאשר קיים קישור ישיר.

## 11. Restore — שחזור

### שחזור לעותק חדש — ברירת המחדל

1. בחירת גיבוי ושרת יעד.
2. בדיקת Docker, ארכיטקטורה, מקום, הרשאות, תלויות ופורטים.
3. הצגת תוכנית שחזור לפני ביצוע.
4. העברת החבילה, אימות ופענוח.
5. טעינת images ויצירת volumes ותיקיות חדשות.
6. שחזור נתונים, בעלות והרשאות.
7. יצירת קונטיינרים ורשתות בשמות נפרדים, עם פורטים נפרדים.
8. הפעלה עם אותן גרסאות תוכנה ובדיקת תקינות.
9. הצגת גישה לעותק ששוחזר והוראות מעבר לאתר הפעיל.

עותק בדיקה אינו מפעיל כברירת מחדל פעולות חיצוניות כגון שליחת מיילים, חיובים או משימות מתוזמנות. חסימת תעבורה והגדרות בדיקה חייבות להיות מפורשות; אין להניח שפעולות כאלה נמנעות מעצמן.

### החלפת אתר קיים

- נדרש אישור מפורש המציג את שם האתר, שרת היעד ותאריך הגיבוי.
- לפני החלפה נוצר גיבוי תקין של האתר הנוכחי באותו תהליך מוסכם. אם הוא נכשל, ההחלפה אינה ממשיכה כברירת מחדל.
- האתר נעצר ונתוניו מוחלפים רק לאחר שהחבילה זמינה ומאומתת ביעד.
- לאחר ההפעלה מבוצעות בדיקות תקינות.
- אם השחזור נכשל, המערכת מנסה להחזיר את המצב הקודם בהתאם ליכולת ההתאוששות ומדווחת על התוצאה. אין להבטיח שהחזרה תמיד תצליח.
- שחזור מסד הנתונים לאחור מחזיר גם את הנתונים לאחור; שינויים מאז מועד הגיבוי לא יופיעו בגרסה המשוחזרת.

שינוי DNS, תעודות TLS, reverse proxy ומעבר דומיין מטופלים כשלב נפרד אם אינם כלולים ביחידת האתר. המערכת מציגה את הדרישות לפני שחזור לשרת אחר.

## 12. תזמון, תורים והתאוששות מכשלים

- אין גיבוי ושחזור מקבילים לאותו אתר.
- ברירת המחדל היא להגביל את מספר האתרים המושבתים במקביל בכל שרת.
- אחרי כיבוי או אתחול של מנהל הגיבויים, מצבי המשימות משוחזרים מהמסד וממצב שרתי המקור.
- פעולות ניתנות לחזרה בטוחה לפי מזהה משימה, בלי ליצור עותקים סותרים.
- מנגנון התאוששות מקומי בשרת המקור מנסה להפעיל מחדש את האתר אם החיבור או שרת הניהול נופלים בזמן ההשבתה. הוא אינו מסתמך רק על finally בתהליך המרכזי.
- ביטול משימה בזמן שהאתר עצור מחייב ניסיון הפעלה מחדש לפני סיום הביטול.
- לא מוחקים נתוני staging של העברה כושלת באופן מיידי; המדיניות מוצגת ומוגבלת כדי למנוע מילוי דיסק.
- timeout או מילוי דיסק בזמן העתקה מבטלים את נקודת הגיבוי ומפעילים תהליך התאוששות לאתר.
- כשל גיבוי וכשל בהפעלת האתר הם מצבים נפרדים, עם התראות נפרדות.

מצבי משימה מוצעים: queued, preflight, stopping, copying, restarting, packing, transferring, verifying, completed, failed, cancelled, recovery_required.

## 13. מקורות חיצוניים אופציונליים

אפשר לצרף bucket, תיקייה בשרת או מקור נוסף דרך מתאם מתאים. כל מקור מוגדר במפורש עם הרשאות והיקף גיבוי. המערכת מציגה אם המקור נכלל ונלכד באותה נקודת זמן.

עקביות של שירות חיצוני אינה מובטחת מעצם עצירת הקונטיינר. מקור חיצוני לא נתמך מוצג כתלות חסרה ולא מסומן כמגובה. התמיכה הזו מיועדת להרחבה; אצל המשתמש כיום הנתונים שייכים לאתר ה־Docker.

## 14. אבטחה

- כניסה מאומתת ל־Dashboard וחיבור HTTPS.
- מפתחות SSH, סודות וגיבויים נשמרים מוצפנים, עם מפתח ראשי שנמצא מחוץ למסד ולגיבויים עצמם.
- אפשרות להוציא ולשמור ערכת התאוששות של מפתחות במקום נפרד.
- SSH host keys מאומתים; אין כיבוי אוטומטי של בדיקת הזהות.
- פקודות מרוחקות נבנות בצורה מבוקרת, ללא שרשור טקסט משתמש לפקודות shell.
- גישה ל־Docker נחשבת להרשאה חזקה על השרת ולכן מוגבלת למנהל מורשה.
- לוגים אינם מכילים סיסמאות, מפתחות או environment רגיש.
- חילוץ חבילות חוסם path traversal, קישורים מסוכנים וכתיבה מחוץ ליעד.
- הורדה, מחיקה, שינוי תזמון ושחזור נרשמים ביומן ביקורת.
- קבצי staging המכילים נתונים רגישים מקבלים הרשאות מוגבלות ונמחקים לפי מדיניות.

## 15. מודל נתונים מוצע

## 16. היקף הגרסה הראשונה

1. מערכת ניהול הניתנת להתקנה באמצעות Docker Compose.
2. הוספת מספר שרתי Linux דרך SSH.
3. זיהוי קונטיינרים ובחירת אתר מלא לגיבוי.
4. מיפוי images, שכבת כתיבה, mounts והגדרות נדרשות.
5. עצירה מסודרת, העתקה מקומית והפעלה מחדש לפני הדחיסה וההעברה.
6. גיבוי ידני וגיבוי מתוזמן עם X גרסאות מוצלחות.
7. אחסון חבילות מלאות עצמאיות בשרת המרכזי.
8. היסטוריה, סטטוסים, לוגים והתראות בסיסיות.
9. הורדת חבילה מלאה והוראות שחזור.
10. שחזור לשרת אחר כעותק חדש, ובהמשך אותו שלב פיתוח גם החלפה מבוקרת של אתר קיים.
11. בדיקות תקינות, התאוששות מהפסקת חיבור וגיבוי של הגדרות מערכת הניהול.

Buckets, גיבוי ללא השבתה, deduplication ו־snapshots מיוחדים הם הרחבות. אין להציג אותם כקיימים לפני מימוש ובדיקה.

## 17. קריטריוני קבלה

- ניתן להוסיף שני שרתים ולגבות אתר מכל אחד דרך אותו Dashboard.
- גיבוי של אתר אינו עוצר אתרי Docker אחרים שאינם חלק מיחידת הגיבוי.
- במהלך הגיבוי נמדדת ההשבתה, והאתר מופעל מחדש לפני דחיסה והעברה.
- שינוי בנתונים הפעילים לאחר ההפעלה אינו משנה את העותק המקומי שנלכד.
- לאחר שמונה גיבויים תקינים עם retention של שבעה, נשארים שבעה רגילים, בנוסף למוצמדים אם קיימים.
- גיבוי שנכשל אינו מוחק נקודת גיבוי תקינה.
- ניתוק SSH או אתחול מנהל הגיבויים בזמן העצירה מפעילים ניסיון התאוששות מקומי ואינם מותירים את האתר כבוי ללא דיווח.
- חבילה שהורדה מכילה את כל הנדרש לשחזור ואינה תלויה ב־image שעדיין זמין ב־registry חיצוני.
- ניתן לשחזר לשרת נקי ותואם, כולל מסד הנתונים, assets, הרשאות והגדרות.
- תוצאות נבדקות באתר אמיתי: קבצים נפתחים, רשומות קיימות, התחברות ופעולות מרכזיות עובדות.
- שחזור לעותק חדש אינו דורס אתר קיים ואינו מפעיל באופן אוטומטי פעולות חיצוניות אמיתיות.
- שחזור שמחליף אתר קיים דורש אישור ויוצר קודם גיבוי תקין של המצב הנוכחי.
- בדיקת checksum מאתרת חבילה פגומה; בדיקת שחזור נפרדת מוכיחה שהגיבוי ניתן להפעלה. אין לבלבל בין שתי הבדיקות.
- הוראות שחזור ומפתח זמין מאפשרים שחזור גם כאשר שרת הניהול המקורי אינו זמין.

## 18. עקרון ההצלחה

המערכת נחשבת מוצלחת כאשר ניתן לבחור גיבוי לפי תאריך ושעה, לשחזר אותו לשרת נקי ותואם, ולהפעיל אתר מלא עם גרסת האפליקציה, מסד הנתונים, ה־assets וכל ההגדרות שנכללו בנקודת הגיבוי — תוך השבתה מוגבלת לשלב יצירת העותק המקומי בעת הגיבוי.

## 19. דף תחזוקה — אפשרות 1 שנבחרה

### מיקום וניהול

ה־Dashboard ומערכת הגיבויים נשארים בשרת הגיבויים המרכזי. בכל שרת אתרים נשמר עותק מקומי של דף תחזוקה סטטי קטן, כולל כל קובצי העיצוב והתמונות הנדרשים לו. אין תלות בשרת הגיבויים או בשירות חיצוני כדי להציג את הדף.

ה־Dashboard מעתיק את הדף לשרתים דרך SSH ומנהל את גרסתו. הדף אינו מוכנס לקונטיינר של האתר שמושבת: הוא מוגש באמצעות Reverse Proxy נפרד, כגון Nginx, שנשאר פעיל בזמן הגיבוי. Proxy אחד יכול לשרת מספר אתרים, עם מצב תחזוקה נפרד לכל אתר ודומיין.

### הגדרה ראשונית

- לכל אתר נרשם מיפוי מפורש בין מזהה האתר, הדומיינים וה־upstream של הקונטיינר.
- הגישה לאתרים עוברת דרך ה־Proxy, שמטפל גם ב־HTTPS ונשאר מחוץ ליחידת העצירה של האתר.
- אם קיים Proxy מתאים, המערכת תומכת בשילוב איתו. שינוי הגדרות קיימות מוצג לבדיקה, נשמר בגיבוי ומאומת לפני החלה.
- בשרת חדש ניתן להתקין Proxy ייעודי עם בדיקת פורטים ותעודות; אין להניח שאפשר להוסיף אותו ללא הגדרת ניתוב.
- אם אין שילוב Proxy פעיל ומאומת, אין להציג דף תחזוקה כמוכן. ברירת המחדל היא לחסום גיבוי מתוזמן של אתר שמוגדר כמחייב דף תחזוקה עד השלמת ההגדרה.
- אין שינוי DNS בכל גיבוי, ואין Redirect לדומיין של שרת הגיבויים. המבקר נשאר בכתובת האתר המקורית.

### תהליך הגיבוי המשולב — מעדכן את סעיף 7

1. ביצוע בדיקות מקדימות, כולל זמינות ה־Proxy ודף התחזוקה.
2. הפעלת מצב תחזוקה רק לאתר שנבחר ואימות שהוא מוצג בכתובת הציבורית.
3. השלמת בקשות פעילות ככל שניתן, הפסקת כתיבות ועצירה מסודרת של קונטיינרי האתר.
4. יצירת עותק מקומי מלא ויציב.
5. הפעלת האתר מחדש, כאשר מצב התחזוקה עדיין פעיל.
6. בדיקת תקינות ישירות מול האתר או בנתיב פנימי ייעודי, כך שהבדיקה אינה מקבלת בטעות את דף התחזוקה.
7. ביטול מצב התחזוקה רק אחרי שהאתר תקין, ובדיקת הגישה הציבורית.
8. דחיסה, הצפנה והעברה לשרת המרכזי כשהאתר כבר זמין.

משך אי־הזמינות למבקר נמדד מהפעלת מצב התחזוקה ועד ביטולו; זמן עצירת הקונטיינר נמדד בנפרד. אין הבטחה למגבלה של שתי דקות או חמש דקות.

### התנהגות הדף

- נוסח ברירת מחדל: „האתר בתחזוקה קצרה. נחזור בעוד דקות בודדות.” ניתן לעריכה ב־Dashboard.
- אפשר להגדיר שם אתר, לוגו, צבעים ונוסח פרטני, או להשתמש בעיצוב אחיד לכולם.
- תגובת התחזוקה היא HTTP 503 עם Retry-After ו־Cache-Control: no-store. אין להציג את התחזוקה כעמוד תקין עם HTTP 200.
- דפדפן בודק במרווחים מתונים נקודת מצב מקומית, עם timeout והשהיה בין ניסיונות. כאשר מצב התחזוקה בוטל, הוא טוען מחדש את כתובת העמוד המקורית.
- אין רענון או שליחה חוזרת אוטומטית של פעולות POST, תשלום או טפסים.
- בקשות API מקבלות תשובת 503 במבנה מתאים ולא עמוד HTML; חיבורי WebSocket עלולים להתנתק ודורשים התחברות מחדש מצד הלקוח.
- תעבורה פעילה שכבר הגיעה לאתר אינה מועברת לדף בדיעבד; מדיניות השלמת בקשות וניתוק חיבורים מוגדרת במפורש.

### כשלים והתאוששות

- אם הפעלת מצב התחזוקה נכשלת, הגיבוי אינו עוצר את האתר.
- אם ההעתקה נכשלת, מנסים להפעיל את האתר מחדש ומבטלים תחזוקה רק לאחר בדיקת תקינות.
- אם האתר אינו עולה, דף התחזוקה נשאר זמין וה־Dashboard שולח התראה ומציג כשל התאוששות.
- מנגנון ההתאוששות המקומי מטפל גם במצב התחזוקה: לאחר הפעלה מוצלחת ובדיקה הוא יכול לבטלו גם אם שרת הגיבויים נותק. timeout לבדו אינו סיבה להסרת דף כאשר האתר עדיין אינו תקין.
- ניתן להפעיל תחזוקה ידנית ולצאת ממנה דרך ה־Dashboard, תוך בדיקת בריאות האתר.
- אתר אחר באותו שרת אינו מושפע מהפעלת תחזוקה או מגיבוי האתר הנבחר.
- הדף מגן מפני השבתת האפליקציה בזמן גיבוי; הוא אינו מבטיח זמינות אם שרת האתר עצמו או ה־Proxy נפלו.

### תוספות לממשק ולבדיקות הקבלה

- מסך ניהול עיצוב דף התחזוקה, תצוגה מקדימה, הפצה וסטטוס גרסה בכל שרת.
- לכל אתר: דומיינים, שילוב Proxy, בדיקת מוכנות, מצב תחזוקה וכפתורי הפעלה וביטול.
- הדף מוצג ב־HTTPS בדומיין המקורי בזמן שהקונטיינר עצור.
- הדף ממשיך להופיע כאשר שרת הגיבויים אינו זמין.
- ביטול התחזוקה לאחר בדיקת תקינות מחזיר מבקר שממתין לעמוד המקורי באמצעות בדיקת מצב ורענון.
- גיבוי של אתר א׳ אינו מפעיל תחזוקה לאתר ב׳ באותו שרת.
- בדיקת בריאות אינה מסתפקת בכך שדף התחזוקה זמין.
- ניתוק מנהל הגיבויים בזמן ההשבתה נבדק גם עבור הפעלה מחדש וגם עבור יציאה תקינה ממצב התחזוקה.
