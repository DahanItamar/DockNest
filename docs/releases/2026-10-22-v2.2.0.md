# DockNest 2.2.0

Released 2026-10-22. [Full changelog](../../CHANGELOG.md). All examples use mock data.

## Summary

DockNest 2.2.0 prepares one-click updates and makes upgrading safer and tidier. It adds an opt-in update check, an optional host updater that you install once, checks that an upgrade target is official, a lock against overlapping upgrades, and automatic removal of old upgrade files. Everyone running 2.1.x can upgrade; read the upgrade notes first, especially the one about the 2.1 to 2.2.0 hop.

## What's new

- **Update Center.** Administrators get an Update Center page. An administrator is asked once whether DockNest may check GitHub for new versions each day; until they say yes nothing is sent ([outbound requests](../security.md#update-checks-outbound-requests)). When a newer release exists, an administrator can start the update after confirming with the password and an authenticator code. While it runs, DockNest shows only an update screen to everyone. Updates are never installed unattended, and downgrades stay a command-line task. In-app updates need the host updater below.
- **Report a bug.** Settings > About opens a pre-filled public GitHub issue with only the DockNest version and install mode. The server sends nothing ([details](../security.md#problem-reports-report-a-bug)).
- **Host updater (optional).** `sudo scripts/install-updater.sh` installs a small root service on the host that can verify a signed release and run the upgrade script, so the containers never need the Docker socket. It refuses rootless Docker, Docker Desktop and a second install ([Host updater and Update Center](../upgrading.md#host-updater-and-update-center)).
- **Official-release check for manual upgrades.** `scripts/upgrade.sh` now requires the target tag to be on `main` and, for 2.2.0 and later, checks the signed `docknest-release.json` with `cosign`. `--no-verify` skips it for forks, mirrors and offline hosts ([Verifying the target](../upgrading.md#verifying-the-target)).
- **Tidy upgrades.** After a successful upgrade the script keeps the newest 5 upgrade backups and the newest 2 rollback copies, and removes only old DockNest images that this installation recorded. Failed and interrupted runs are kept for you. `--no-prune` turns it off ([What is removed after an upgrade](../upgrading.md#what-is-removed-after-an-upgrade)).

## Improved

- **One upgrade at a time.** A lock (`data/.upgrade.lock`) stops two `upgrade.sh` runs from overlapping.
- **Real client addresses behind a proxy (optional).** By default DockNest trusts no proxy, so behind Caddy all browsers share the proxy's address in rate limiting. Set `TRUST_PROXY` to your proxy's exact address or CIDR to use the real one ([security](../security.md#client-address-and-trust_proxy)).
- **Fewer manual rollbacks.** If the new release fails its health check after only compatible schema changes, the script now restores the previous release automatically and exits 4, instead of exit 5 with manual steps. The image built for the failed target is removed.
- **Richer release manifest.** `docknest-release.json` now names the tag, commit, repository and pre-release flag, optional release highlights and the host updater file hashes, and is signed with a `.sigstore.json` bundle that the release workflow verifies before publishing.

## Fixed

- The deployment hold now also waits for a queued or running DockNest self-backup before an upgrade proceeds, so an upgrade cannot start in the middle of one.
- A recovery kit taken during a deployment hold no longer restores a manager that refuses all work: exporting is refused while the hold is on, and a restore clears the hold. A restore also refuses while the host updater reports a running update (`--ignore-updater` overrides this for disaster recovery).

## Security

None. The new outbound requests of the update check are listed in [security.md](../security.md#update-checks-outbound-requests); they happen only after an administrator agrees. Security reports go through [SECURITY.md](../../SECURITY.md).

## Upgrade notes

Read these before upgrading. The upgrade and rollback commands are in [docs/upgrading.md](../upgrading.md).

1. **The 2.1.x to 2.2.0 hop runs the 2.1 script.** `scripts/upgrade.sh` from your current checkout does the work, so this one upgrade has no official-release check, no cleanup of old files, no exit 4 after a compatible migration, and the 2.1 deployment hold does not pause self-backups. Run it outside your self-backup window. Every later upgrade uses the 2.2.0 script. You can run the 2.2.0 script directly with `git show v2.2.0:scripts/upgrade.sh`.
2. **The metadata schema moves from 4 to 5.** The new migration only adds tables, so 2.1.x can still run on the upgraded database and rolling back needs no snapshot restore.
3. **Cleanup now deletes old files.** Earlier releases never deleted upgrade backups. From the first 2.2.0-script upgrade onward, only the newest 5 upgrade backups and newest 2 rollback copies in the state volume remain, plus those of failed or interrupted runs, and only this installation's old images are removed. Older rollback copies cannot be restored later; you would pull or rebuild that release. Use `--no-prune` to keep everything. Copy `data/master.key` to a safe place regardless.
4. **Manual upgrades need `curl` and `cosign`** to check the signed manifest. Without `cosign` the signature check is skipped with a warning. On a host without access to GitHub pass `--no-verify`.
5. **The host updater is optional.** Nothing changes unless you run `sudo scripts/install-updater.sh`. A new `docknest_updater` Docker volume appears with this release; it stays empty without the updater.

## Known limits

- The Update Center page in this release candidate calls a few read-only routes (release details, the What's new notes) that the API does not serve yet; the page then says the notes could not be loaded. The pre-update checks page, the full changelog tab, the activity timeline and failed-update reports to GitHub are planned for 2.3.0 ([update-center.md](../update-center.md)).
- Downgrades stay a command-line task. The host updater only upgrades.
- The host updater supports rootful Docker on systemd Linux only, one install per host.
- Self-update of the host updater and a read-only "check" action are planned for 2.3.0; until then `sudo scripts/install-updater.sh --repair` reinstalls it.
- S3-compatible storage is still beta, as in 2.1.
