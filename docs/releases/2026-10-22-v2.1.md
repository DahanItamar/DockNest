# DockNest 2.1

Released 2026-10-22. [Full changelog](../../CHANGELOG.md). All examples use mock data.

## Summary

DockNest 2.1 makes upgrading existing installations safer: versioned metadata migrations with a snapshot before every schema change, a one-command upgrade and rollback script, and signed container images. It also adds S3-compatible backup storage (beta) and shows what was actually checked for each backup. Everyone running 2.0.0 should read the upgrade notes first.

## What's new

- **Safe upgrades.** Metadata migrations are now versioned. Before any schema change DockNest writes a private snapshot to `DATA_DIR/upgrade-snapshots` (the newest five are kept). A release refuses to start on a newer schema and names the snapshot to restore. `scripts/upgrade.sh` upgrades, rolls back and downgrades with one command ([upgrading](../upgrading.md)).
- **S3-compatible backup storage (beta).** AWS S3, Cloudflare R2, Backblaze B2, Wasabi and MinIO, next to SFTP. Uploads stream in parts, publication is verified before it counts, and optional S3 Object Lock keeps immutable copies. Run a restore test before relying on it.
- **Honest verification levels.** Each backup shows four separate results: integrity checked, consistency verified, isolated restore tested and application checks passed, each with the time it was last checked. Older backups that were integrity-checked before 2.1 still show as checked.
- **A worker that recovers by itself.** The single-worker lock is now an expiring lease in the database. A worker that was killed no longer blocks its replacement, and a stopped worker finishes its current job before exiting.
- **Signed images and a release manifest.** Container images are published on GitHub Container Registry (`ghcr.io/dahanitamar/docknest`), signed with cosign, with a `docknest-release.json` manifest on each release. Release notes are bundled in the image. Building from source stays the default ([published image](../upgrading.md#use-the-published-image)).
- **Running version in the app.** A public `GET /api/version` endpoint returns the version and schema version, and the preferences drawer shows the running version with a link to the releases page. There is no automatic update check.

## Improved

- **Faster dashboard.** The overview loads verification results in one query, and history is available through paginated API endpoints.
- **Clearer backup status.** Status labels describe what was actually checked instead of a single "Verified" label, and status marks use the shared icon set instead of text characters.
- **Boot recovery reports its age.** Boot recovery reports `bootRecoveryOutdated` when the helper copied onto a host differs from the running release.
- **Local Compose changes.** `compose.override.yaml` (ignored by git) holds local Compose changes, with an example file.

## Fixed

- A worker killed during a job no longer blocks its replacement after restart.
- A concurrent first start of the API and worker no longer fails with "database is locked".
- Flaky SFTP test fixtures caused by an ssh2 key-generation bug (test-only; no change for users).

## Security

- Probe URLs are resolved once on the source server, every address is checked, connections are pinned to the checked address, redirects may not leave the host or downgrade to HTTP, and each probe has one total time limit. Health and maintenance probe URLs can no longer reach cloud metadata, link-local or other internal addresses from your servers.
- Release images are signed with cosign and published with a `docknest-release.json` manifest. See [docs/upgrading.md](../upgrading.md#use-the-published-image) for the verification command.

## Upgrade notes

Read these before upgrading an existing 2.0.0 installation.

1. **First upgrade from 2.0.0 is manual.** 2.0.0 has no upgrade script. From the DockNest checkout run `git fetch --tags && git checkout v2.1.0 && docker compose up -d --build`. The new release snapshots the metadata before migrating. From 2.1 onward use `scripts/upgrade.sh` ([docs/upgrading.md](../upgrading.md)).
2. **Your configuration is unchanged.** `.env`, `data/master.key`, `data/setup.token`, volume names and ports stay as they are. Put any local Compose changes in `compose.override.yaml`, which upgrades never touch.
3. **Rolling back.** 2.0.0 can run on the upgraded metadata, because every 2.1 schema change only adds tables and indexes. To return to 2.0.0, check out `v2.0.0` and rebuild. No data is discarded.
4. **Reinstall boot recovery.** Servers where boot recovery was installed keep an older helper copy. The site's boot recovery status reports it as outdated; reinstall it for each affected site.
5. **Sites with a private-IP health URL keep backing up.** If a site's health or maintenance URL points to a private IP address (for example a container address), backups continue with that probe skipped and a warning on every job. Edit the URL to the site's domain or a loopback port to restore the HTTP health check.
6. **Worker stop grace period.** The worker now drains on stop and Compose waits up to five minutes for it. Jobs that run longer are stopped and reported as needing recovery review, as before.

## Known limits

- **S3-compatible storage is beta.** Its adapter is tested in CI against a MinIO-compatible server (the pinned pgsty/minio fork) and an in-process fake; not yet against real providers. Full Linux backup and restore over S3 has not been validated yet.
- The upgrade path is validated end to end on a disposable Linux Docker host with seeded 2.0.0 data, not on a production installation. Back up as usual before upgrading.
- The in-app update check and one-click update arrive in 2.2.

## Validation

- **Tested:** 2.1.0 has the same application code as the pre-release 2.1.0-rc.1 (`src/` and `web/` unchanged; the pre-release is no longer listed). The release candidate passed the real upgrade validation from 2.0.0 on a Linux Docker runner, and the v2.1.0 tag itself also passed Release validation: install 2.0.0, upgrade as documented, worker drain, downgrade to 2.0.0 and upgrade again with `scripts/upgrade.sh`, checking data, configuration and secrets. See [release validation](../release-validation.md).
- **Not covered by that run:** it uses seeded data, so no real backup or restore over SSH is part of it. Published-image mode and cosign verification are not exercised. It starts only from 2.0.0 on a single host and exercises the HTTP API, not the dashboard. [Release validation](../release-validation.md#what-it-does-not-prove) lists the rest.
