# DockNest 2.1

Release candidate `2.1.0-rc.1` published 2026-10-22. All examples use mock data.

## Highlights

- **Safe upgrades.** Metadata migrations are now versioned. Before any schema change DockNest writes a private snapshot to `DATA_DIR/upgrade-snapshots` (the newest five are kept). A release refuses to start on a newer schema and names the snapshot to restore. `scripts/upgrade.sh` upgrades, rolls back and downgrades with one command.
- **S3-compatible backup storage (beta).** AWS S3, Cloudflare R2, Backblaze B2, Wasabi and MinIO, next to SFTP. Uploads stream in parts, publication is verified before it counts, and optional S3 Object Lock keeps immutable copies. Run a restore test before relying on it.
- **Honest verification levels.** Each backup shows four separate results: integrity checked, consistency verified, isolated restore tested and application checks passed, each with the time it was last checked. Older backups that were integrity-checked before 2.1 still show as checked.
- **A worker that recovers by itself.** The single-worker lock is now an expiring lease in the database. A worker that was killed no longer blocks its replacement, and a stopped worker finishes its current job before exiting.
- **Probe URL hardening.** Health and maintenance probe URLs can no longer reach cloud metadata, link-local or other internal addresses from your servers.
- **Faster dashboard.** The overview loads verification results in one query, and history is available through paginated API endpoints.

## Upgrade notes

Read these before upgrading an existing 2.0.0 installation.

1. **First upgrade from 2.0.0 is manual.** 2.0.0 has no upgrade script. From the DockNest checkout run `git fetch --tags && git checkout v2.1.0-rc.1 && docker compose up -d --build`. The new release snapshots the metadata before migrating. From 2.1 onward use `scripts/upgrade.sh` ([docs/upgrading.md](../upgrading.md)).
2. **Your configuration is unchanged.** `.env`, `data/master.key`, `data/setup.token`, volume names and ports stay as they are. Put any local Compose changes in `compose.override.yaml`, which upgrades never touch.
3. **Rolling back.** 2.0.0 can run on the upgraded metadata, because every 2.1 schema change only adds tables and indexes. To return to 2.0.0, check out `v2.0.0` and rebuild. No data is discarded.
4. **Reinstall boot recovery.** Servers where boot recovery was installed keep an older helper copy. The site's boot recovery status reports it as outdated; reinstall it for each affected site.
5. **Sites with a private-IP health URL keep backing up.** If a site's health or maintenance URL points to a private IP address (for example a container address), backups continue with that probe skipped and a warning on every job. Edit the URL to the site's domain or a loopback port to restore the HTTP health check.
6. **Worker stop grace period.** The worker now drains on stop and Compose waits up to five minutes for it. Jobs that run longer are stopped and reported as needing recovery review, as before.
7. **S3 storage is beta.** Its adapter is tested against a real MinIO server in CI. Full Linux backup and restore over S3 has not been validated yet.

## Security

- Probe URLs are resolved once on the source server, every address is checked, connections are pinned to the checked address, redirects may not leave the host or downgrade to HTTP, and each probe has one total time limit.
- Release images are signed with cosign and published with a `docknest-release.json` manifest. See [docs/upgrading.md](../upgrading.md) for the verification command.

## Known limitations

- `scripts/upgrade.sh` and the release workflow have been tested in CI with test doubles and a real 2.0.0 database, not yet on a production host. This is why 2.1 starts as a release candidate.
- The in-app update check and one-click update arrive in 2.2.
